# v0.1.3 HK2/RK Mode Matrix

Date: 2026-06-24

This document records live mode-by-mode measurements between the HK2 client
host and the RK server host. It is intentionally practical: the same proxy,
same benchmark sink, same 32 MiB object, and the same log-risk gate were used
for every recorded mode.

## Feature Status

| Capability | Status in v0.1.3 | Notes |
| --- | --- | --- |
| Dynamic HKDF handshake window | Implemented | `shared.handshake_window` derives first-packet keys by time slot. |
| Same-window first-packet replay hardening | Implemented | Authenticated first packet digests are cached before any response. |
| Multi-lane TCP pool | Implemented | `local.tunnel_pool` splits streams across independent physical TCP lanes. |
| Stealth frames and shaper | Implemented | Fixed-size frames plus optional budgeted idle padding/timing shaping. |
| WebSocket underlay | Implemented | HTTP/1.1 Upgrade, then binary WebSocket frames. |
| HTTP/2 underlay | Implemented and tuned | v0.1.3 adds configurable h2 flow-control windows. |
| Deterministic port hopping | Implemented | Client selects the active port by time window; server binds candidates. |
| Physical UDP/FEC underlay | Not production | Core UDP primitives exist, but TCP/yamux remains production transport. |

## Mode Configuration

### TCP Auto-Throughput

Best first choice for raw speed on VPS links.

```bash
espejismo-remote --profile auto-throughput --config server.toml
espejismo-local  --profile auto-throughput --config client.toml
```

Key parameters:

| Parameter | Typical value | Effect |
| --- | ---: | --- |
| `local.tunnel_pool.max_connections` | `8` | Maximum physical TCP lanes. |
| `local.tunnel_pool.interactive_lanes` | `1` | Reserved small-flow lane count. |
| `local.tunnel_pool.bulk_lanes` | `6` | Bulk-flow lane count. |
| `shared.obfuscation.max_chunk` | `262127` through profile | Larger encrypted frames for bulk traffic. |
| `shared.tcp.send_buffer_bytes` / `recv_buffer_bytes` | at least `4194304` | Larger kernel socket buffers. |

### Stealth

Use this when packet shape and timing matter more than throughput. The live
32 MiB throughput run intentionally shows the cost: this profile is not the
bulk-transfer profile.

```bash
espejismo-remote --profile stealth --config server.toml
espejismo-local  --profile stealth --config client.toml
```

Key parameters:

| Parameter | Example | Effect |
| --- | --- | --- |
| `shared.stealth.frame_size_candidates` | `[3328, 3584, 4096, 4608]` | Narrows visible encrypted frame sizes. |
| `shared.stealth.tick_ms` | `20` | Cadence for stealth frame emission. |
| `shared.stealth_shaper.mode` | `web` | Adds browser-like idle decay. |
| `shared.stealth_shaper.padding_budget_bps` | `16384` | Caps cover-traffic byte cost. |

### WebSocket Underlay

Useful when a path, reverse proxy, or operational environment expects a
WebSocket-looking TCP flow.

```toml
[shared.underlay]
mode = "websocket"

[shared.underlay.websocket]
path = "/espejismo"
max_frame_bytes = 1048576
# host = "example.com"
```

Client and server must use the same `path`. `host` is client-side only and
changes the HTTP Host header.

### HTTP/2 Underlay

Useful for controlled h2 underlay tests or a reverse-proxy deployment. The
underlay itself is cleartext prior-knowledge h2; put it behind TLS/ALPN at a
front proxy if public HTTPS semantics are required.

```toml
[shared.underlay]
mode = "http2"

[shared.underlay.http2]
path = "/espejismo"
initial_stream_window_bytes = 8388608
initial_connection_window_bytes = 16777216
max_frame_bytes = 65536
# authority = "example.com"
```

v0.1.3 makes the h2 flow-control windows configurable. The previous default h2
window behaved correctly but was too small for the HK2/RK high-latency path.

### Port Hopping

Useful when operators want a deterministic rotating port set without changing
the cryptographic tunnel above it.

```toml
[shared.port_hopping]
enabled = true
ports = [6694, 16694, 26694, 36694]
window_secs = 60
seed = "change-me-shared-port-hop-seed"
```

The server binds every configured candidate port. The client chooses one
candidate per `window_secs` using the shared seed and current Unix time slot.
Open every candidate in the server firewall.

## Recommendations

| Scenario | Recommended mode | Why |
| --- | --- | --- |
| Normal Windows client to Ubuntu VPS | `--profile auto-throughput` | Best speed/efficiency on the tested path. |
| Reverse-proxy-friendly TCP flow | `underlay.websocket` | Kept 89-104% efficiency in this run. |
| HTTP/2 controlled underlay | `underlay.http2` | Now performs close to WebSocket/TCP with tuned windows. |
| Rotating server port set | `shared.port_hopping` | Near TCP efficiency while changing the selected client port by time window. |
| Highest low-feature traffic shaping | `--profile stealth` | Use only when cover traffic and timing shaping are more important than speed. |

For production bulk use, start with `auto-throughput`, enable
`handshake_window`, keep logs at `info`, and validate with
`scripts/bench-throughput.sh` after every config change.
